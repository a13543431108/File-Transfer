五、UDP-RTP 可靠通道 + SYNC 校时
================================================================================

   两端各自：收到对方 UDP 打洞探测包（P2P_UDP_HOLE）
              │
              ▼
   ┌──────────────────────────────────────────┐
   │ 建立 UDP-RTP 可靠通道（共享 udp_hole_sock）  │
   │  · 12B 包头：type/seq/ack/length/reserved   │
   │  · type: DATA=0 ACK=1 FIN=2 KEEPALIVE=3     │
   │          SYNC_REQ=4 SYNC_ACK=5 SYNC_COMMIT=6│
   │          PUNCH_ROUND=7 TCP_READY=8 PUNCH_FAIL=9│
   │  · 重传(RTO 300ms) / 滑窗 / 按序重组          │
   └────────────────────┬─────────────────────┘
                        │
                        ▼
   ┌──────────────────────────────────────────┐
   │ 若 my_id < peer_id → 作为 initiator 发起 SYNC │
   │  · 采样 4 次：SYNC_REQ(t1, ver)              │
   │  · 对端回 SYNC_ACK(t1,t2,t3, ver)            │
   │  · 算 RTT / offset（NTP 公式）取最小 RTT 那次  │
   └────────────────────┬─────────────────────┘
                        │
                        ▼
   ┌──────────────────────────────────────────┐
   │ 发 SYNC_COMMIT 约定 TCP 打洞时刻             │
   │  · v2(payload !QQ)：t_go_R(对端钟) + commit_id│
   │    重传 3 次(幂等)，对端按 commit_id 去重      │
   │  · v1 兼容：delta 相对时刻，单发               │
   └────────────────────┬─────────────────────┘
                        │
                        ▼
   两端到 t_go 时刻 → 进入【六、TCP 打洞流程】

六、TCP 打洞流程（优化版）
================================================================================

   [触发源] 以下任一即可发起打洞：
     · 服务器 punch_go(对端 pub_tcp + 统一 at 时刻)
     · 对端 TCP_READY（#6：映射就绪信号）
     · SYNC_COMMIT 约定时刻（第五节）
              │
              ▼
   ┌──────────────────────────────────────────┐
   │ 构造候选地址（#4 UDP 端口预测）             │
   │  1) 内网地址(v4/v6) + 对端 TCP 端口          │
   │  2) TCP 公网映射 (pub_tcp)                  │
   │  3) pub_tcp 为空 → UDP 打洞端口 ±2 预测       │
   └────────────────────┬─────────────────────┘
                        │
                        ▼
   ┌──────────────────────────────────────────┐
   │ #3 候选【并行】connect（非串行）             │
   │  · Barrier 对齐各候选起跑                    │
   │  · 所有候选同时 connect（自适应超时#9）        │
   │  · 谁先成功用谁，其余关闭                     │
   └────────────────────┬─────────────────────┘
                        │
              ┌─────────┴─────────┐
              │ 成功               │ 失败
              ▼                    ▼
   ┌──────────────────┐   ┌──────────────────────────┐
   │ 得到长连接        │   │ #2 轮次确定性对齐           │
   │ 保持打开          │   │  · my_id < peer → 主导：    │
   │ 通知 TCP_READY    │   │    下发 PUNCH_ROUND(下一轮时刻)│
   └────────┬─────────┘   │  · my_id > peer → 跟随：    │
            │             │    等到主导方时刻再打          │
            │             │  · 无 UDP 通道 → 本地退避      │
            │             └──────────┬───────────────┘
            │                        │ 轮次用尽
            │                        ▼
            │             ┌──────────────────────────┐
            │             │ 标记 FAILED               │
            │             │ #8 发 PUNCH_FAIL 通知对端   │
            │             │ （守卫：仅未连接时才标失败）  │
            │             └──────────────────────────┘
            ▼
   ┌──────────────────────────┐
   │ 启动接收循环              │
   │ 用 io_lock 串行化收发      │
   └──────────────────────────┘

   并发控制：Semaphore(6) 限制同时打洞任务数
   关键守卫：任务结束时若 peer 已被其他任务连接 → 静默退出，
             不覆盖 CONNECTED、不发 PUNCH_FAIL

七、打洞优化机制（P2 #1~#9）
================================================================================

   ┌──────┬────────────────────────┬──────────────────────────────┐
   │ 编号 │ 机制                    │ 作用                           │
   ├──────┼────────────────────────┼──────────────────────────────┤
   │  #1  │ COMMIT 可靠化+版本协商   │ 单包丢失不报废；重传零漂移      │
   │  #2  │ 轮次确定性对齐           │ 多轮重试两端不再错位            │
   │  #3  │ 候选并行连接             │ 天然对齐，首轮耗时降至 1×超时   │
   │  #4  │ UDP 端口预测             │ pub_tcp 为空时也能打通          │
   │  #6  │ TCP 就绪信号             │ 省掉前几轮"空打"，缩短建连      │
   │  #8  │ 失败即时通知             │ 对端不再空等满超时              │
   │  #9  │ 自适应超时               │ 高 RTT 放长窗口，低 RTT 快速重试│
   └──────┴────────────────────────┴──────────────────────────────┘

   协议版本：PROTO_VER=2（新↔新走 v2；新↔旧自动回退 v1，不崩溃）
   传输路径：全部经 UDP-RTP 直连，不经服务器 → 服务器无需重新部署

八、梯度冗余多路径调度（V16）
================================================================================

  打洞成功后，同一 peer 维护多条路径，按 RTT 分级、按角色保活、可换路续传。

  ┌─────────────────────────────────────────────────────┐
  │ 打洞成功（可能多候选）→ 按 RTT 分级                    │
  │   最小 → 热备 hot（传数据）                            │
  │   次小 → 保守暖备 warm_safe（硬性钳制，确保可立即接管）│
  │   第三 → 宽松暖备 warm_loose（贪心省电）              │
  └──────────────────────┬──────────────────────────────┘
                         │
  ┌──────────────────────▼──────────────────────────────┐
  │ 保活：软性探测 + 硬性下限                             │
  │   · 成功 → 间隔指数增长（逼近 NAT 超时）              │
  │   · 失败 → 与已知成功值二分收敛                       │
  │   · 硬性下限：TCP≥30s / UDP≥15s                       │
  │   · 保守暖备硬性钳制 ≤ 协议安全上限（TCP3600/UDP60）  │
  └──────────────────────┬──────────────────────────────┘
                         │
  ┌──────────────────────▼──────────────────────────────┐
  │ 空闲降频（连接池复用）                                │
  │   传输结束不关连接 → 下次直接复用                     │
  │   空闲越久保活越稀疏：<60s×1 → <10min×4 → <1h×16 → ×64│
  └──────────────────────┬──────────────────────────────┘
                         │
  ┌──────────────────────▼──────────────────────────────┐
  │ 热备断裂 → 立即重建                                   │
  │   1) 保守暖备上位为热备                               │
  │   2) 宽松暖备验证后升级为保守暖备                     │
  │   3) 后台立即重建补足宽松暖备                         │
  │   4) 跨路径重传未确认部分                             │
  └──────────────────────┬──────────────────────────────┘
                         │
  ┌──────────────────────▼──────────────────────────────┐
  │ 按角色选路发送（hot → warm_safe → warm_loose）        │
  │   通道失败 → 换另一条路径重发（最多 3 次）            │
  │   · 单文件：QUERY_OFFSET 协商从断点继续               │
  │   · 文件夹：重新握手，接收端 skip/resume/full         │
  └─────────────────────────────────────────────────────┘

十二、信令服务器状态机
================================================================================

   全局状态：rooms / id_index / tcp_mappings / tcp_socks（受 state_lock 保护）

   ┌────────────┐   join    ┌──────────────────────────────────┐
   │   空闲      │──────────►│ 校验房间号                        │
   └────────────┘           │  · 房间满 → 回 ROOM_FULL          │
                            │  · 新建/加入房间                  │
                            │  · 登记成员（pub=来源地址）        │
                            │  · 回 joined + 广播 member_join   │
                            │  · save_state()                   │
                            └──────────────┬───────────────────┘
                                           │
              ┌────────────────────────────┼────────────────────────────┐
              │ hb                          │ punch_req                  │ bye / 超时
              ▼                             ▼                            ▼
   ┌──────────────────┐         ┌──────────────────────┐     ┌──────────────────┐
   │ 刷新 last_hb      │         │ 校验双方同房间         │     │ remove_member     │
   │ 更新 pub          │         │ 下发 punch_go 给双方   │     │  · 移除成员        │
   └──────────────────┘         │ (统一 at 时刻)         │     │  · 关闭TCP映射连接 │
                                └──────────────────────┘     │  · 广播 member_leave│
                                                             │  · save_state()    │
                                                             └──────────────────┘

             保持连接打开（维持 NAT 映射）

九、房间密码（V16.1 新增）
================================================================================

  首位加入者决定房间性质：

    ┌──────────────────────┐
    │ 用户输入 房间号 + 密码 │
    └──────────┬───────────┘
               │
       ┌───────┴────────┐
       │ 密码为空？       │
       └───┬────────┬───┘
        是 │        │ 否
           ▼        ▼
   ┌───────────┐  ┌────────────────────┐
   │ 开放房间   │  │ 受保护房间（须匹配）  │
   │ 谁都能进   │  │ 密码错 → 拒绝        │
   └───────────┘  └────────────────────┘
               │
               ▼
   服务器校验（锁内原子）：
     · 房间开放 + 客户端带密码   → ROOM_OPEN
     · 房间受保护 + 客户端没密码 → NEED_PASSWORD
     · 密码不匹配                → BAD_PASSWORD
     · 通过 → joined(room_open=...)
               │
               ▼
   房间空了 → 房间 + 密码 一并彻底删除

   兼容性：不填密码 → 报文与旧版逐字节一致（零兼容风险）
